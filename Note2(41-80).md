# The Rule of Three and The Law of the Big Two

## The Rule of Three
The **Rule of Three** is a fundamental best-practice guideline in C++ regarding resource management and class design. 

### The Rule
If your class requires you to explicitly define **any one** of the following three special member functions, it is highly likely that you need to explicitly define **all three** (and usually a fourth: the copy assignment operator).
1. **Destructor**
2. **Copy Constructor**
3. **Copy Assignment Operator**

### Explanation
When you rely on compiler-generated default constructors and destructors, C++ performs **shallow copies** and trivial destruction. 
* If your class dynamically allocates memory on the heap (using `new` or `malloc`), a shallow copy will result in two objects pointing to the exact same memory address. 
* When both objects go out of scope, the destructor will attempt to `delete` the same memory twice, causing a **Double Free** crash.
* Therefore, if you write a custom constructor that allocates memory, you *must* write a custom **Destructor** to free it, and you *must* write custom **Copy Constructors** and **Copy Assignment Operators** to allocate new memory and perform a **Deep Copy**.

## The Law of the Big Two
A lesser-known, modern corollary to the Rule of Three.

### The Rule
If your class manages its resources using standard library containers (like `std::vector`) or Smart Pointers, you **do not** need to define a custom Destructor, but you might still want to define a custom **Constructor** and **Copy Constructor/Assignment**.

### Explanation
Because standard library containers like `std::vector` automatically manage their own heap memory and clean up after themselves, you do not need to manually call `delete` in a custom destructor. The compiler-generated default destructor is sufficient. However, you might still need a custom constructor or copy constructor if you require specific custom initialization logic (e.g., populating the vector in a non-standard way during construction).

# Where the Copy Constructor is Called

Understanding exactly when C++ invokes a Copy Constructor is crucial for performance and bug prevention.

## The Triggers
A copy constructor is called whenever a new object is created and initialized using an existing object.
1. **Direct Initialization:** `MyArray arr2 = arr1;` or `MyArray arr2(arr1);`
2. **Pass by Value (Crucial):** When an object is passed as a parameter to a function by value.

## The Pass by Value Performance Trap
By default, C++ passes arguments by value. If you pass a massive object (e.g., an array of 1,000,000 integers) into a function by value, C++ **silently invokes the copy constructor** to duplicate the entire object into the function's local scope.

```cpp
// DANGER: Passes by value. Invokes a massive, expensive copy!
void printArray(Array a) {
    // ...
}

int main() {
    Array myArray; // Allocates 1,000,000 items
    
    for (int i = 0; i < 100; i++) {
        printArray(myArray); // Creates 100 massive copies of the array!
    }
}
```

## Solutions to Prevent Accidental Copies

### 1. Pass by Reference
Always pass large objects by reference (and use `const` if you aren't modifying them) to avoid the copy constructor entirely.
```cpp
// Highly Efficient: Passes the memory address alias. NO copy is made.
void printArray(const Array& a) {
    // ...
}
```

### 2. Explicitly Delete the Copy Constructor (Modern C++)
If you have an object that is so large or uniquely owning that it should **never** be copied under any circumstances, you can explicitly forbid copies using `= delete`.

```cpp
class Array {
public:
    // Tells the compiler: DO NOT generate a copy constructor.
    // If anyone tries to copy this object, throw a compile error.
    Array(const Array& rhs) = delete; 
    
    // (In older C++, the equivalent was making the copy constructor private).
};
```

# Operator Overloading

Operator overloading allows you to redefine how standard C++ operators (`+`, `-`, `++`, `<<`, `==`, etc.) behave when applied to your custom User-Defined Types (classes/structs).

## Core Concept
Operators are just functions under the hood. For example, `x = a + b` is essentially evaluated as `x = a.operator+(b)`.

## Binary Operators (e.g., `+`)
Binary operators require two operands (a Left-Hand Side and a Right-Hand Side). 

```cpp
class Vector3f {
public:
    float x, y, z;

    Vector3f() { x = 0.0f; y = 0.0f; z = 0.0f; }

    // Operator Overload for '+'
    // 'const' at the end ensures the LHS object is not modified.
    Vector3f operator+(const Vector3f& rhs) const {
        Vector3f result;
        result.x = this->x + rhs.x;
        result.y = this->y + rhs.y;
        result.z = this->z + rhs.z;
        return result; // Returns a brand new object
    }
};
```

## Unary Operators: Prefix Increment (`++`)
Unary operators apply to a single operand.

```cpp
class Vector3f {
public:
    float x, y, z;

    // Operator Overload for Prefix '++' (e.g., ++myVector)
    // Returns a reference to the modified current object
    Vector3f& operator++() {
        this->x += 1.0f;
        this->y += 1.0f;
        this->z += 1.0f;
        return *this; 
    }
};
```

## Stream Insertion Operator (`<<`)
To allow printing your object directly using `std::cout << myObj`, you must overload the `<<` operator. 
* **Important:** Because the Left-Hand Side of the operation is `std::ostream` (not your class), this is usually implemented as a **Free Function** outside the class (or as a `friend` function if it needs access to private data).

```cpp
#include <iostream>

// Free function implementation
std::ostream& operator<<(std::ostream& os, const Vector3f& obj) {
    os << obj.x << ", " << obj.y << ", " << obj.z;
    return os;
}

int main() {
    Vector3f v;
    std::cout << v << '\n'; // Will output "0, 0, 0"
}
```

## Comparison Operator (`==`) and Floating Point Caveats
Overloading the equality operator allows you to check if two objects are conceptually identical.

```cpp
// Free function implementation for equality
bool operator==(const Vector3f& lhs, const Vector3f& rhs) {
    return (lhs.x == rhs.x && lhs.y == rhs.y && lhs.z == rhs.z);
}
```

### The Floating-Point Warning
**Never directly compare floats with `==`.** Due to hardware precision limitations, floats that should mathematically be equal might have minor differences in binary representation, causing `==` to incorrectly evaluate to `false`.
* **Actual Best Practice:** Subtract the two values, take the absolute value, and check if it is smaller than a tiny threshold (epsilon).

## Other Notable Operators
* `new` and `delete`: Can be overloaded to write custom memory allocators/trackers.
* `operator()`: The function call operator (creates "Functors").
* `operator<`: Required to use standard algorithms like `std::sort` on custom objects.

# Member Initializer Lists

A **Member Initializer List** is a highly efficient, modern C++ syntax used inside constructors to initialize member variables *before* the constructor body executes.

## Mechanics of Object Construction
When an object is created without an initializer list:
1. Memory is allocated for the object.
2. Every member variable is **default-constructed**.
3. The constructor's body `{}` executes, typically performing **assignments** (re-writing the already-constructed values).

This two-step process (construct -> assign) is inefficient, especially for complex types like `std::string`. 

## Syntax and Benefits
Using an initializer list directly constructs the member variable with the target value, saving a step and boosting performance.
* **Syntax:** A colon `:` placed after the constructor signature, followed by a comma-separated list of `variable(value)`.

```cpp
// Inefficient (Default Construction + Assignment)
Vector3f::Vector3f() {
    x = 1.0f;
    y = 2.0f;
    z = 3.0f;
}

// Highly Efficient (Direct Construction via Initializer List)
Vector3f::Vector3f() : x(1.0f), y(2.0f), z(3.0f) {
    // Constructor body can be empty!
}
```

## The Crucial Rule: Initialization Order
The order in which variables are initialized is strictly dictated by **the order they are declared in the class header**, NOT the order you write them in the initializer list.

### The Bug Example
```cpp
class Vector3f {
public:
    float x;
    float y;
    float z;

    // BUG: You wrote 'y' first in the list, relying on 'z'.
    // However, the compiler looks at the class declaration and sees 'y' 
    // is declared BEFORE 'z'. 
    // It will try to initialize 'y' first using an uninitialized 'z' (garbage data).
    Vector3f() : y(z), z(2.0f), x(3.0f) {} 
};
```
**Best Practice:** Always write your member initializer list in the exact same order the variables are declared in your class.

## Interface vs. Implementation Placement
When separating code into `.hpp` (interface) and `.cpp` (implementation) files, the Member Initializer List goes exclusively in the **`.cpp` implementation file**.

```cpp
// Vector3f.hpp (Interface)
class Vector3f {
public:
    float x, y, z;
    Vector3f(); // Declaration only
};

// Vector3f.cpp (Implementation)
#include "Vector3f.hpp"

// Initializer list belongs here
Vector3f::Vector3f() : x(0.0f), y(0.0f), z(0.0f) {
}
```

# Classes vs. Structs in C++

## The Core Difference
In C++, a `struct` and a `class` are functionally identical. They can both contain member variables, member functions, constructors, and destructors.

There is exactly **one** difference between them:
* **`class`:** Members and inheritance default to **`private`**.
* **`struct`:** Members and inheritance default to **`public`**.

```cpp
// Everything here is PRIVATE by default
class MyClass {
    int x; // Cannot be accessed outside MyClass
};

// Everything here is PUBLIC by default
struct MyStruct {
    int x; // Can be accessed anywhere
};
```

## Why Do Both Exist?
C++ was built on top of the C programming language. In C, `struct` was used to group "Plain Old Data" (POD) together, without any functions or access modifiers. C++ had to retain the `struct` keyword for backwards compatibility with C code.

## When Should You Use Which?
* **Use `class`** when your object has complex invariants, requires encapsulation (information hiding), and has an active role in managing its state via constructors/member functions.
* **Use `struct`** when your object is just a simple, passive container for data (e.g., `Vector3f` holding `x, y, z` coordinates), and you want direct, public access to its variables without the overhead of writing getter and setter methods.

# RAII (Resource Acquisition Is Initialization)

## What is RAII?
RAII is a fundamental programming paradigm unique to C++ and Rust. It ensures that resource management (memory, file handles, network sockets, mutex locks) is inextricably tied to the **lifetime of an object** using block scope `{}`.

### The Problem it Solves
In languages like C, if you allocate memory or lock a thread, you must remember to manually free or unlock it. If an error or exception occurs before you hit the unlock/free code, the resource leaks, causing a deadlock or crash.

### The RAII Solution
1. **Resource Acquisition (Constructor):** A resource is acquired (allocated, opened, locked) inside an object's constructor.
2. **Resource Release (Destructor):** The resource is freed (deleted, closed, unlocked) inside the object's destructor.
3. Because C++ guarantees that destructors are **automatically** called when an object goes out of scope (even if an exception is thrown and the program panics), the resource is 100% guaranteed to be cleaned up safely.

## Real-World Examples
* **Smart Pointers:** `std::unique_ptr` wraps heap memory. When it leaves scope, its destructor calls `delete`.
* **Threading:** `std::lock_guard` wraps a Mutex. It locks the mutex in its constructor and unlocks it in its destructor.
* **File I/O:** `std::fstream` opens a file upon creation and automatically closes the file handle when destroyed.

# The Rule of Five

If your class manually manages a resource (like raw heap memory pointers), you are governed by the Rule of Five (an expansion of the Rule of Three introduced in C++11).

## The Five Special Member Functions
If you must implement one of these, you must implement a policy for **all five**:
1. **Destructor:** To free the resource.
2. **Copy Constructor:** To deep-copy the resource into a new object.
3. **Copy Assignment Operator:** To deep-copy the resource into an existing object.
4. **Move Constructor:** To "steal" the resource from a temporary rvalue without copying.
5. **Move Assignment Operator:** To "steal" the resource into an existing object.

## Defining a Move Constructor
The Move Constructor takes an **rvalue reference (`&&`)**. Instead of allocating new memory and copying the data, it takes the memory pointer from the temporary source object, points to it, and sets the source's pointer to `nullptr`.

```cpp
class Array {
private:
    int* m_data;
public:
    // Move Constructor
    Array(Array&& source) {
        m_data = source.m_data; // 1. Steal the memory address
        source.m_data = nullptr; // 2. Nullify the source so its destructor doesn't delete our stolen memory
    }
};
```

## Why Move Semantics Matter (Performance)
If you place objects into a `std::vector` (using `.push_back()`), the vector often resizes internally. If you only have a copy constructor, the vector will physically copy every single element into new memory space (which requires hundreds of allocations and memory reads). If you define a move constructor, the vector simply shifts the pointers around, reducing allocations drastically (e.g., from 52 allocations down to 13), increasing speed by orders of magnitude.

*(Note: Modern C++ allows you to write `= delete;` next to these functions to explicitly forbid copying or moving).*

# The `friend` Keyword

## What is a `friend`?
In C++, data encapsulation ensures that `private` members cannot be accessed outside the class. However, the `friend` keyword allows a class to grant special, direct access to its `private` and `protected` members to specific outside functions or other classes.

## Friend Functions
You can declare an external free function as a friend by placing the `friend` keyword and the function signature inside your class body.

```cpp
class UserData {
private:
    int m_secretCode = 42;

    // Grant this specific external function access to private data
    friend void printSecret(UserData u); 
};

// Free function
void printSecret(UserData u) {
    // Because it is a friend, it can access m_secretCode directly
    std::cout << u.m_secretCode << '\n'; 
}
```

## Friend Classes
You can also grant an entire external class access to your private data.
* **Important:** Friendship is a **one-way** relationship. If Class A grants friendship to Class B, Class B can read Class A's private data. But Class A *cannot* read Class B's private data unless Class B explicitly grants friendship back.

```cpp
class SecurityInfo {
private:
    int m_passcode = 1234;

    // Grants the 'UserData' class full access to SecurityInfo's private members
    friend class UserData; 
};
```

## Best Practices and Code Smells
**The General Rule:** Avoid using the `friend` keyword.
* **Why?** It breaks encapsulation and violates the core principles of Object-Oriented design. If multiple unrelated functions or classes start peering directly into private member variables, the code becomes highly coupled, fragile, and hard to refactor.
* **Security Vulnerability:** A malicious programmer can create a class matching the exact name of your declared friend class to forcefully extract your private data.
* **Acceptable Use Cases:** The main acceptable use case for `friend` functions is when implementing specific operator overloads, specifically the stream insertion operator (`operator<<`), which is technically external to the class but requires deep read access to format the class data for the console.


# The `explicit` Keyword for Constructors

## Implicit Conversions
By default, if a C++ constructor takes exactly one argument, the compiler is allowed to perform **implicit conversions** (automatic type casting) to match that constructor. 
* **The Problem:** If you have a custom class `MyType` that takes an `int`, and you accidentally pass a `float` (like `500.5f`), the compiler will silently truncate it to `500` and construct the object without throwing an error. This can lead to subtle bugs where wrong data types or "magic numbers" are passed around.

## The `explicit` Keyword
You can prevent this silent compiler behavior by adding the keyword `explicit` before the constructor declaration.

* **Behavior:** It strictly forbids the compiler from performing implicit conversions or using copy-initialization syntax (`MyType t = 500;`). 
* **Best Practice:** You should generally make single-argument constructors `explicit` unless you have a specific reason to allow implicit conversions (like in certain mathematical libraries).

```cpp
class UserDefinedType {
public:
    // Prevents implicit conversions (e.g., from float to int)
    explicit UserDefinedType(int i) { 
        // ...
    }
};

int main() {
    // UserDefinedType u1 = 500;   // ERROR: Copy-initialization not allowed
    // UserDefinedType u2(500.5f); // ERROR: Implicit narrowing float->int not allowed
    
    // Correct way
    UserDefinedType u3(500); 
    UserDefinedType u4{500}; // Modern list initialization (preferred)
}
```

# Object-Oriented Programming: Inheritance

## What is Inheritance?
Inheritance is a core pillar of Object-Oriented Programming (OOP) that allows you to create a new class based on an existing class.
* **Base Class (Parent):** The existing class that provides common attributes and behaviors.
* **Derived Class (Child/Subclass):** The new class that inherits everything from the Base Class and can add its own unique attributes and behaviors.

### The "Is-A" Relationship
Inheritance establishes an **"Is-A"** relationship. 
* Example: A `GoldenRetriever` **is a** `Dog`. Therefore, a `GoldenRetriever` class should inherit from a `Dog` class. It will automatically know how to `bark()` and `walk()`, but you can also give it a unique `retrieve()` function.

## Basic Syntax

```cpp
class Dog { // Base Class
public:
    void bark() { std::cout << "Bark!\n"; }
};

// Derived Class publicly inheriting from Dog
class GoldenRetriever : public Dog { 
public:
    void retrieve() { std::cout << "Fetching stick...\n"; }
};

int main() {
    GoldenRetriever myDog;
    myDog.bark();     // Inherited from Dog
    myDog.retrieve(); // Unique to GoldenRetriever
}
```
*(Note: A derived class will always be larger in memory (`sizeof`) than its base class if it adds new member variables, because it physically contains all the data of the base class plus its own).*

# Access Modifiers and Inheritance

When inheriting, the access modifiers (`public`, `protected`, `private`) determine what the Derived class can see, and what the outside world (e.g., `main()`) can see.

## 1. Internal Access (What the Derived Class can see)
Inside the code of the Derived class itself:
* **`public` base members:** Accessible.
* **`protected` base members:** Accessible. (This is the primary purpose of `protected`: hiding data from the outside world, but allowing child classes to use it).
* **`private` base members:** **NOT Accessible.** They belong exclusively to the Base class.

## 2. Inheritance Access Specifiers (`public`, `protected`, `private`)
When you define the inheritance (e.g., `class Derived : public Base`), you dictate how the Base class's members are exposed to the *outside world* through the Derived class.

| Inheritance Type | Base `public` members become... | Base `protected` members become... | Base `private` members become... | Use Case |
| :--- | :--- | :--- | :--- | :--- |
| **`public Base`** | `public` | `protected` | Inaccessible | The standard "Is-A" relationship. |
| **`protected Base`** | `protected` (Demoted) | `protected` | Inaccessible | Niche. Often used in Java/C# ports. |
| **`private Base`** | `private` (Demoted) | `private` (Demoted) | Inaccessible | "Has-A" relationship implemented via inheritance. Hides the base class entirely from the outside world. |

# Constructor Delegation in Inheritance

When you instantiate a Derived class, memory is allocated for the Base class portion first, then the Derived class portion. Therefore, constructors must be called in a specific order.

## Order of Construction and Destruction
* **Construction:** Top-down. The Base constructor executes first, then the Derived constructor.
* **Destruction:** Bottom-up (Reverse order). The Derived destructor executes first, then the Base destructor.

## Calling Specific Base Constructors
If your Base class does not have a default (zero-argument) constructor, the compiler will throw an error when you try to create a Derived class, because it doesn't know how to construct the Base portion. 

You must explicitly call the Base class's constructor from the Derived class's **Member Initializer List**.

```cpp
#include <iostream>
#include <string>

class Entity {
public:
    std::string m_name;
    // Base constructor takes 1 argument
    Entity(std::string name) : m_name(name) {
        std::cout << "Entity Constructed\n";
    }
};

class Monster : public Entity {
public:
    // The Derived class constructor MUST explicitly call the Base constructor
    Monster(std::string name) : Entity(name) {
        std::cout << "Monster Constructed\n";
    }
};
```

## Multi-Level Inheritance Restrictions
If you have a deep hierarchy (`TopLevel` -> `Entity` -> `Monster`), a class can **only** explicitly call the constructor of its *direct* parent.
* A `Monster` cannot explicitly call the `TopLevel` constructor in its initializer list. It must pass the required data to the `Entity` constructor, and the `Entity` constructor must pass it up to `TopLevel`.
* **Best Practice:** Keep inheritance hierarchies shallow. Deep, nested inheritance (more than 2 or 3 levels) creates fragile, difficult-to-maintain code architectures.




# Inheritance-Based Polymorphism and Dynamic Dispatch

## The Polymorphism Problem
When using inheritance, a Base class pointer can legally point to a Derived class object in memory. 

```cpp
// Legal: A Derived object IS-A Base object
Base* instance = new Derived(); 
```

**The Problem:** By default, C++ uses **static dispatch** (early binding). The compiler looks at the *pointer type* (`Base*`), not the *actual object type* in memory (`Derived`). If both classes share a member function name, calling `instance->memberFunc()` will mistakenly execute the Base class's version.

## The Solution: `virtual` and `override`

### `virtual` Keyword
* **Definition:** A keyword applied to a Base class member function to indicate that its behavior can be overridden by a derived class.
* **Explanation:** Marking a function as `virtual` tells the C++ compiler to use **Dynamic Dispatch** (late binding). It instructs the program to determine the actual object type at runtime and call the correct, most-derived member function.

### `override` Keyword (Modern C++11)
* **Definition:** A specifier applied to a Derived class member function to explicitly state that it is overriding a virtual function from a Base class.
* **Explanation:** While technically optional, it is a strict best practice. It forces the compiler to check the Base class. If the function signature is misspelled or doesn't actually exist in the Base class, the compiler will throw an error, preventing silent bugs.

### Syntax and Example

```cpp
#include <iostream>

class Base {
public:
    virtual void memberFunc() { 
        std::cout << "Base member function called\n"; 
    }
};

class Derived : public Base {
public:
    // 'override' ensures we are correctly overriding a Base virtual function
    void memberFunc() override { 
        std::cout << "Derived member function called\n"; 
    }
};

int main() {
    Base* instance = new Derived();
    
    // Outputs "Derived member function called" because of 'virtual'
    instance->memberFunc(); 
    
    delete instance;
    return 0;
}
```

## Explicitly Calling a Base Member Function
If you have overridden a function but have a specific edge-case where you *must* execute the Base class's implementation, you can bypass dynamic dispatch using the scope resolution operator (`::`).

```cpp
// Explicitly forces the Base class version to run
instance->Base::memberFunc(); 
```

# Virtual Destructors and Memory Safety

## The Memory Leak Problem
If you dynamically allocate a Derived object and assign it to a Base pointer, calling `delete` on that pointer invokes the destructor. 
* **If the Base destructor is NOT virtual:** Only the Base class destructor runs. The Derived class destructor is completely ignored. 
* **The Impact:** Any heap memory (e.g., `new int[15]`) allocated specifically inside the Derived class will leak, causing a major resource loss.

## The Solution: `virtual` Destructors
**Rule:** If a class is intended to be used as a Base class for polymorphism, its destructor **must** be marked `virtual`.

### Explanation
Making the Base destructor `virtual` guarantees that C++ looks down the inheritance hierarchy at runtime, finds the most-derived destructor, and executes destructors in the correct order (Derived destructor first, then Base destructor).

### Code Example
```cpp
#include <iostream>

class Base {
protected:
    int* m_baseData;
public:
    Base() { m_baseData = new int[10]; }
    
    // MUST be virtual to ensure Derived destructor is called
    virtual ~Base() { 
        delete[] m_baseData; 
        std::cout << "Base destroyed\n";
    }
};

class Derived : public Base {
private:
    int* m_derivedData;
public:
    Derived() { m_derivedData = new int[15]; }
    
    ~Derived() override { 
        delete[] m_derivedData; // Safely cleans up Derived memory
        std::cout << "Derived destroyed\n";
    }
};

int main() {
    Base* instance = new Derived();
    
    delete instance; // Safely outputs: Derived destroyed -> Base destroyed
    return 0;
}
```

# Under the Hood: The Virtual Table (`vtable`)

To enable Dynamic Dispatch at runtime, C++ compilers use a hidden mechanism known as the Virtual Table (`vtable`).

### Mechanism Breakdown
1. **The `vtable`:** As soon as a class contains at least one `virtual` function (or inherits one), the compiler generates a hidden lookup table for that specific class. This table contains memory pointers mapped to the correct implementations of the virtual functions for that class.
2. **The `vptr` (Virtual Pointer):** The compiler adds a hidden member variable (typically 4 or 8 bytes) to every *instance* (object) of a polymorphic class. This is the `vptr`.
3. **Runtime Execution:** 
   * When an object is created, its `vptr` is initialized to point to the `vtable` of its actual instantiated class.
   * When `ptr->virtualFunc()` is called, the program executes a lookup: it follows the object's `vptr` to the `vtable`, finds the correct memory address for `virtualFunc`, and executes it.

### Example Walkthrough
* `Base* b = new Derived();`
* A `Derived` object is created in memory.
* Its hidden `vptr` is set to point to the `Derived` class's `vtable`.
* When `b->memberFunc()` is invoked, C++ follows the `vptr` to the `Derived` `vtable` and executes `Derived::memberFunc`.
* If you delete the object and reassign the pointer: `b = new Base();`, the new object's `vptr` points to the `Base` `vtable`, and future calls execute `Base::memberFunc`.

# Abstract Classes and Interfaces

In languages like Java or C#, `interface` is a dedicated keyword. In C++, interfaces are conceptual constructs implemented using **Pure Virtual Functions**.

## Pure Virtual Functions (`= 0`)
* **Definition:** A virtual function in a Base class that has no implementation. It is declared by appending `= 0` to the function signature.
* **Explanation:** This enforces a strict contract. It tells the compiler: *"This function MUST be overridden and implemented by any Derived class."*

## Abstract Classes
* **Definition:** Any class containing at least one Pure Virtual Function becomes an **Abstract Class**.
* **Rule:** You **cannot instantiate** an Abstract Class. (e.g., `IRenderer* r = new IRenderer();` throws a compiler error: *"invalid new expression of abstract class type"*). 

## C++ Interfaces
An interface in C++ is simply an Abstract Class where *all* member functions are pure virtual, representing a pure contract without any implementation logic.
* **Convention:** Interface classes are typically prefixed with a capital `I` (e.g., `IRenderer`).

### The Benefit
Interfaces future-proof code and force consistency across development teams. If the `OpenGL` team and the `Vulkan` team both inherit from `IRenderer`, they are forced to use the exact function names (e.g., `draw()`). They cannot invent team-specific names (like `drawOptimized()` vs `drawOptimizedVK()`), preventing API fragmentation.

### Interface Implementation Example

```cpp
#include <iostream>

// INTERFACE (Abstract Class)
class IRenderer {
public:
    // Pure Virtual Functions
    virtual void draw() = 0;   
    virtual void update() = 0; 
    
    // Virtual destructor required for safe polymorphic cleanup
    virtual ~IRenderer() = default; 
};

// DERIVED CLASS 1
class OpenGL : public IRenderer {
public:
    // MUST implement draw() and update(), otherwise OpenGL also becomes abstract
    void draw() override { 
        std::cout << "OpenGL draw\n"; 
    }
    void update() override { 
        std::cout << "OpenGL update\n"; 
    }
};

// DERIVED CLASS 2
class Vulkan : public IRenderer {
public:
    void draw() override { 
        std::cout << "Vulkan draw\n"; 
    }
    void update() override { 
        std::cout << "Vulkan update\n"; 
    }
};

int main() {
    // IRenderer* r = new IRenderer(); // COMPILE ERROR: Cannot instantiate abstract class
    
    // Valid: Base pointer to Derived object
    IRenderer* myRenderer = new OpenGL(); 
    myRenderer->draw(); // Outputs: OpenGL draw
    
    // Easily swappable at runtime
    delete myRenderer;
    myRenderer = new Vulkan();
    myRenderer->draw(); // Outputs: Vulkan draw
    
    delete myRenderer;
    return 0;
}
```


# Multiple Inheritance

## What is Multiple Inheritance?
Multiple inheritance is a feature in C++ that allows a derived class to inherit from more than one base class simultaneously.
* **Syntax:** `class Derived : public Base1, public Base2 { ... };`

## The Diamond Problem
Multiple inheritance often leads to structural complexities, the most famous being the **Diamond Problem**.

### Scenario
1. You have a base class `Dog`.
2. `Golden` inherits from `Dog`.
3. `BorderCollie` inherits from `Dog`.
4. A new class `Trevor` (a mix) inherits from **both** `Golden` and `BorderCollie`.

### The Ambiguity Error
If `Dog` has a virtual member function `bark()`, and both `Golden` and `BorderCollie` override this function, what happens when you call `bark()` on a `Trevor` object?
* The compiler cannot determine which version of `bark()` to execute (the one inherited from `Golden` or the one from `BorderCollie`).
* This ambiguity causes a **compiler error**.
* Resolving these ambiguities requires explicit scope resolution or virtual inheritance, which makes the codebase highly complex and difficult to maintain.

### Best Practice
* **Avoid deep multiple inheritance.** Many modern languages (like Java and C#) ban multiple class inheritance entirely, forcing the use of interfaces instead.
* In C++, it is generally considered a red flag unless used for specific design patterns, such as **Mixins** or behavioral policies.

## Valid Use Case: Policy/Mixin Classes (e.g., `NonCopyable`)
One highly practical use case for multiple inheritance is inheriting specific, isolated traits to restrict or add behavior. 

### The `NonCopyable` Pattern
You can create a class whose sole purpose is to delete its copy constructor and copy assignment operator.

```cpp
struct NonCopyable {
    // Force compiler to create default constructor
    NonCopyable() = default; 
    
    // Delete copy semantics
    NonCopyable(const NonCopyable& rhs) = delete;
    NonCopyable& operator=(const NonCopyable& rhs) = delete;
};

// Dog inherits normal traits but also inherits the "NonCopyable" trait
class Dog : public NonCopyable {
    // ...
};

int main() {
    Dog dog1;
    // Dog dog2 = dog1; // COMPILE ERROR: Use of deleted function
    return 0;
}
```
* **Benefit:** By inheriting from `NonCopyable`, the `Dog` class is instantly protected from being accidentally copied or passed by value. It acts as a strict layer of safety enforced by the compiler.

# `const` Correctness in Classes

Applying the `const` keyword correctly throughout your codebase is known as **Const Correctness**. It leaves strict clues for the compiler and other programmers about what data is allowed to be modified.

## The Three Uses of `const`

### 1. Read-Only Variables (Immutable State)
Prevents a local variable from being modified after it is initialized.
```cpp
const int myNumber = 5;
// myNumber = 10; // COMPILE ERROR
```

### 2. Read-Only Parameters
Prevents a function from accidentally modifying the arguments passed to it. Essential when passing large objects by reference (`const std::string&`).
```cpp
void setValue(const int number) {
    // number = 72; // COMPILE ERROR
}
```

### 3. Read-Only Member Functions (Class Specific)
You can append the `const` keyword to the end of a class member function signature.
* **Definition:** It guarantees that calling this function will **not modify any member variables** (state) of the object.
* **Why use it?** If you have a "getter" function (`getValue()`), it should strictly retrieve data, not mutate it. Marking it `const` enforces this design and prevents accidental side-effects (e.g., assigning a value when you meant to use `==`).
* **Thread Safety:** Marking functions as `const` makes it easier to reason about thread safety because you are guaranteed no internal state changes will occur during the read operation.

```cpp
class UserDefinedType {
private:
    int m_value;

public:
    void setValue(int newValue) { 
        m_value = newValue; // Mutates state, CANNOT be const
    }

    // Marked as const: guarantees read-only access
    int getValue() const {
        // m_value = 10; // COMPILE ERROR: Cannot mutate in a const function
        return m_value;
    }
};
```

# Initialization Syntax and `std::initializer_list`

C++ has multiple syntaxes for initializing variables and objects. Understanding the difference between parentheses `()` and curly braces `{}` is critical in Modern C++.

## Primitive Initialization Options
```cpp
int a = 4;   // Copy initialization
int b(4);    // Direct initialization
int c{4};    // Brace/List/Uniform initialization (Modern C++)
```

## The Power of Curly Braces `{}`: Preventing Narrowing Conversions
If you attempt to initialize an integer with a floating-point number using parenthesis or equals, C++ will silently truncate the decimal (e.g., `4.5` becomes `4`). 
**Curly braces strictly forbid narrowing conversions.**

```cpp
int x(4.5); // Compiles: x silently becomes 4
int y{4.5}; // COMPILE ERROR: Narrowing conversion from float to int
```
* **Best Practice:** Use `{}` initialization to make your code safer and force explicit types.

## `std::initializer_list`
Modern C++ provides `<initializer_list>`, a lightweight standard library container used to iterate through a braced list of elements. 

You can define a custom constructor that takes a `std::initializer_list`, allowing users to create objects identically to how they create standard arrays or `std::vector`s.

```cpp
#include <initializer_list>
#include <iostream>

struct MyCollection {
    // Constructor taking an initializer_list
    MyCollection(std::initializer_list<int> data) {
        std::cout << "Initializer list constructor called!\n";
        for (int element : data) {
            std::cout << element << " ";
        }
    }

    // Standard constructor with 3 parameters
    MyCollection(int a, int b, int c) {
        std::cout << "3-Parameter constructor called!\n";
    }
};
```

## Constructor Precedence: `()` vs `{}`

When instantiating an object, the syntax you choose radically alters which constructor the compiler prefers.

| Syntax | Example | Behavior / Precedence |
| :--- | :--- | :--- |
| **Parentheses `()`** | `MyCollection u(1, 2, 3);` | Calls the standard 3-parameter constructor. Will completely ignore `std::initializer_list` constructors. |
| **Curly Braces `{}`** | `MyCollection u{1, 2, 3};` | **Strongly prefers** the `std::initializer_list` constructor. If an `initializer_list` constructor exists, it will hijack the call and route all elements to it. |
| **Fallback `{}`** | (Assume `initializer_list` constructor does *not* exist in the class) | Falls back to the 3-parameter constructor, but still enforces the strict **no-narrowing-conversions** rule. |



# Composition vs. Aggregation

Both composition and aggregation represent a **"has-a"** relationship between classes (as opposed to inheritance, which is an **"is-a"** relationship). They are used to keep inheritance hierarchies flat and avoid unnecessarily complex derivations. The key distinction between the two lies in **object lifetime and ownership**.

| Feature | Composition | Aggregation |
| :--- | :--- | :--- |
| **Relationship** | "Has-a" | "Has-a" |
| **Lifetime** | Tied to the containing object. When the container is destroyed, the composed objects are destroyed. | Not necessarily tied to the containing object. The aggregated object can outlive the container. |
| **Implementation** | Member variables (e.g., objects by value). | Pointers or references to objects stored elsewhere. |
| **Ownership** | Strict ownership. The container creates and destroys the object. | Shared or external ownership. The object is created externally and passed in. |

### Composition Example
The `Point2D` instances are created and destroyed exactly when the `Character` is created and destroyed.
```cpp
struct Point2D {
    int x, y;
};

class Character {
private:
    Point2D position;  // Composition: Character "has-a" position
    Point2D direction; // Composition
};
```

### Aggregation Example
The `homeBase` exists outside the character's scope (e.g., as a global variable or in another system). The `Character` merely holds a reference to it.
```cpp
class Character {
private:
    Point2D& refHome; // Aggregation: Reference to an external object

public:
    // Must be initialized using a member initializer list
    Character(Point2D& homeBase) : refHome(homeBase) {} 
};

// Usage:
Point2D globalHome{0, 0}; 
Character mike(globalHome); // globalHome outlives 'mike'
```

# Multiple Inheritance and The Diamond Problem

Multiple inheritance allows a class to inherit from more than one base class. However, it can lead to the **Diamond Inheritance Problem**.

### The Diamond Problem
Occurs when a base class (`Entity`) is inherited by two intermediate classes (`Warrior` and `Goblin`), and a derived class (`Player`) inherits from both intermediate classes.

```text
      Entity (x, y)
       /       \
  Warrior     Goblin
       \       /
        Player
```
By default, `Player` will inherit **two separate copies** of `Entity`'s member variables (two `x`s and two `y`s). Accessing `mike.x` becomes **ambiguous**, resulting in a compiler error.

### Solution 1: Explicit Scoping (Not Recommended)
You can resolve the ambiguity by specifying which copy you want, but this duplicates memory unnecessarily.
```cpp
Player mike;
mike.Warrior::x = 10;
mike.Goblin::x = 20; 
```

### Solution 2: Virtual Inheritance
To ensure that only **one copy** of the base class member variables is inherited, you must use **virtual inheritance** when deriving the intermediate classes. 

```cpp
class Entity {
public:
    int x, y;
};

// Use 'virtual' keyword to merge base class variables
class Warrior : virtual public Entity {};
class Goblin : virtual public Entity {};

class Player : public Warrior, public Goblin {};

// Usage:
Player mike;
mike.x = 10; // No longer ambiguous. Only one 'x' exists.
```

**Important Caveat:** 
Virtual inheritance only resolves duplicate members originating from the *shared base class*. If `Warrior` and `Goblin` independently define a variable with the same name (e.g., `int power;`), accessing `power` from `Player` will still be ambiguous. This often indicates a design flaw where `power` should have been placed higher up in the hierarchy or implemented via composition.

# C++ Classes and OOP Core Concepts

## 1. Class vs. Struct

| Concept | `struct` | `class` |
| :--- | :--- | :--- |
| **Default Visibility** | `public` | `private` |
| **Default Inheritance** | `public` | `private` |
| **Usage Convention** | Often used for **POD (Plain Old Data)** types (C-style structs containing only data members). | Used for objects requiring encapsulation and complex logic. |

## 2. RAII (Resource Acquisition Is Initialization)
One of the most important concepts in modern C++.
*   **Definition:** Resources (heap memory, file handles, network sockets, thread locks) should be acquired in an object's **constructor** and released in its **destructor**.
*   **Why it's important:** It ties resource management to object lifetime. This guarantees exception safety and prevents resource leaks because C++ guarantees destructors are called when an object goes out of scope.

## 3. Special Member Functions

If you do not provide them, the C++ compiler will generate trivial default versions of the constructor, destructor, and copy constructor.

### Copy Constructor
Called when an object is initialized from another object of the same type.
*   **Syntax:** `ClassName(const ClassName& other);`
*   **When you need a custom one:** Any time you are performing a **deep copy** (e.g., when a class manages dynamically allocated memory via pointers). A compiler-generated shallow copy would copy pointer addresses, leading to double-free errors.

### Move Constructor (C++11)
Called when an object is initialized from an **rvalue** (`&&`). 
*   **Behavior:** Instead of allocating new memory and copying data, it transfers (moves) ownership of the resources from the temporary rvalue object to the new object.

### The Rule of Three vs. The Rule of Five
Rules dictating which special member functions you must explicitly define to safely manage resources.

| The Rule of Three (Legacy C++) | The Rule of Five (Modern C++11 and later) |
| :--- | :--- |
| If you define **one** of the following, you should define **all three**: | If you define **one**, you should define **all five** (especially to support move semantics): |
| 1. Destructor<br>2. Copy Constructor<br>3. Copy Assignment Operator | 1. Destructor<br>2. Copy Constructor<br>3. Copy Assignment Operator<br>4. Move Constructor<br>5. Move Assignment Operator |

## 4. Preventing Object Copies
Sometimes objects represent unique resources that should not be copied.
*   **Modern C++ (C++11 onwards):** Use the `= delete` keyword on the copy constructor and copy assignment operator.
*   **Legacy C++ (Pre-C++11):** Declare the copy constructor and copy assignment operator as `private` and do not provide an implementation.

## 5. Construction and Initialization

### Uniform Initialization: Braces `{}` vs. Parentheses `()`

| Syntax | Behavior | Caveat / Advantage |
| :--- | :--- | :--- |
| `Type obj(1, 2);` | Direct initialization | Allows **narrowing conversions** (e.g., passing `2.4` to an `int` silently truncates it to `2`). |
| `Type obj{1, 2};` | List/Uniform initialization | **Prevents narrowing conversions** (throws a compiler error if you pass a `float` to an `int`). Also prefers `std::initializer_list` constructors if they exist. |

### Member Initializer Lists
Always initialize class member variables using a member initializer list rather than assigning them inside the constructor body.
*   **Why:** It avoids making unnecessary copies or double-initialization (default-constructing an object and then reassigning it). It directly constructs the member in place, which is crucial for performance.

```cpp
class Example {
    int x;
public:
    // Good: Member initializer list
    Example(int val) : x(val) {} 
    
    // Bad: Assignment inside body (causes overhead for complex types)
    // Example(int val) { x = val; } 
};
```

## 6. Inheritance Details

### Order of Construction and Destruction
When inheriting, memory and resources must be built from the ground up and torn down in reverse.
*   **Construction:** Base class constructor is called FIRST, then the Derived class constructor.
*   **Destruction:** Derived class destructor is called FIRST, then the Base class destructor.

### Virtual Destructors
*   **Rule:** If a class is meant to be a base class, its destructor **must be virtual**.
*   **Why:** If you delete a derived object through a base class pointer (`Base* ptr = new Derived(); delete ptr;`), a non-virtual base destructor will only destroy the base portion of the object. A `virtual` destructor ensures the `Derived` destructor is called first, preventing memory leaks.

### Virtual Functions and V-Tables
*   **Virtual Function:** Enables **dynamic dispatch** (runtime polymorphism). It ensures the correct derived class function is called when accessed via a base class pointer or reference.
*   **V-Table (Virtual Table):** The underlying mechanism C++ uses to support dynamic dispatch. Each class with virtual functions gets a hidden v-table (an array of function pointers). Each object gets a hidden pointer (v-ptr) to this table to look up the correct function at runtime.

### Abstract Classes
*   C++ does not have an `abstract` keyword.
*   An abstract class (often used as an interface) is created by defining at least one **pure virtual function** using `= 0`.
*   Any derived class **must** implement this function to be instantiated.

```cpp
class IRenderer {
public:
    virtual void draw() = 0; // Pure virtual function
    virtual ~IRenderer() = default; 
};
```

## 7. Additional C++ Class Nuances

### `const` Correctness
The `const` keyword has three primary uses:
1.  **Local Variables:** Marks a variable as read-only.
2.  **Parameters:** Prevents modifying arguments (often used as `const Type&` to pass large objects efficiently without copying or allowing modification).
3.  **Member Functions:** Placed after a method signature (`void print() const;`), it guarantees the function will not modify any member variables of the class.

### `.hpp` (Header) vs `.cpp` (Source)
*   **Headers:** Serve as an interface. Contain declarations, class blueprints, and member variables. No complex logic.
*   **Source files:** Contain the proprietary implementation code.
*   **Why:** Hides implementation details and significantly speeds up compilation. If only the implementation changes, the `.cpp` file is recompiled without forcing every file that included the header to recompile.

### Friend Classes
Declaring a class as a `friend` gives that external class access to all `private` and `protected` member variables and functions. (Breaks strict encapsulation, so use it sparingly).

### Operator Overloading
Allows you to define how C++ operators (`+`, `-`, `<<`, `==`, `new`, `delete`) interact with user-defined types (e.g., overloading `+` for a `Vector3` math class).

### The `this` Pointer
*   `this` is a **pointer** to the current object, not a reference.
*   **Historical context:** It is a pointer simply because it was added to the language (C with Classes) before references even existed in C++.

# Value Initialization and Zeroing Memory

If you create an object or struct and do not initialize its fields, C++ will leave them uninitialized. Primitive types (`int`, `float`, pointers) will contain **junk values** left over in memory.

### Zero-Initialization via Braces `{}`
To guarantee everything is zeroed out, you can use empty curly braces:

```cpp
struct Entity {
    std::string name;
    int x, y;
    int* collection;
};

// Value Initialization
Entity e{}; 
```
**Results of `{}` initialization:**
*   `x` and `y` are initialized to `0`.
*   `collection` pointer is initialized to `nullptr` (`0`).
*   `name` calls the `std::string` default constructor (empty string).

### Interaction with Constructors

The behavior of `{}` changes based on whether a constructor is provided:

1.  **No constructor provided:** `Entity e{};` zero-initializes all members.
2.  **Constructor explicitly defaulted (`= default`):**
    ```cpp
    class Entity {
    public:
        Entity() = default; 
        int x, y;
    };
    ```
    `Entity e{};` **will** zero-initialize all primitive members.
3.  **User-defined empty constructor:**
    ```cpp
    class Entity {
    public:
        Entity() {} // User provided, but empty
        int x, y;
    };
    ```
    `Entity e{};` **will NOT** zero-initialize primitive members. `x` and `y` will hold random junk values because the compiler defers strictly to the user-provided constructor (which does nothing).

**Best Practice:**
If your struct is just a collection of data (POD type like a 3D vector), do not provide an empty constructor so that users can utilize `{}` to safely zero-initialize it. If you do provide a constructor, explicitly set the values to `0` inside a member initializer list.


# Value Initialization and In-Class Initialization

In C++, leaving variables uninitialized can lead to them holding random "junk" values left over in memory. Modern C++ provides multiple ways to initialize member variables directly to avoid this.

## Zero Initialization vs. Uninitialized

When creating an instance of a class/struct:
*   `Entity e;` (without curly braces) leaves primitive types uninitialized if no constructor is defined, resulting in random values.
*   `Entity e{};` (with curly braces) zero-initializes the object. All primitive members will be set to `0` (or `nullptr` for pointers), and object members will call their default constructors.

## In-Class Initializers

You can provide default values for member variables directly in the class definition. 

### Syntax
```cpp
class Entity {
public:
    int x{0};          // Preferred: Prevents narrowing conversions
    int y = 0;         // Valid, but uses assignment syntax
    int* data{nullptr};
    std::string name{"Default"};
};
```

### Why use `{}` instead of `()` or `=`?
Using curly braces `{}` is preferred because it prevents **narrowing conversions**. 
*   If you write `int x{5.2};`, the compiler will throw an error. 
*   If you use parenthesis or assignment (in certain contexts), the compiler might silently cast `5.2` to `5`, which can lead to bugs. 
*   Note: You cannot use parenthesis for in-class initialization (e.g., `int x(4);` is invalid because the compiler parses it as a function declaration).

## Initialization Precedence Rules

If an object is initialized using multiple methods simultaneously, C++ follows a strict precedence order to determine which value is ultimately assigned:

1.  **Constructor Member Initializer List (Highest Precedence):** Values provided here override everything else.
2.  **In-Class Initializer:** Used if the member is omitted from the constructor's initializer list.
3.  **Zero Initialization `{}` (Lowest Precedence):** Applied if no in-class initializer exists, no constructor member initializer exists, and the object is instantiated with `{}`.

# Delegate Constructors and the DRY Principle

The **DRY (Don't Repeat Yourself)** principle states that duplication in logic should be avoided. In object-oriented programming, a common violation of DRY occurs when multiple constructors in the same class need to perform the same setup logic.

## The Anti-Pattern: The `init()` Function
Developers often attempt to solve constructor duplication by writing a private `init()` or `startup()` function and calling it inside every constructor.

**Why this is bad:**
1.  You have to remember to call `init()` in every new constructor.
2.  It prevents you from using the **Member Initializer List**, forcing you to use assignment inside the function body (which is less efficient).
3.  It creates an artificial function that shouldn't exist in the class design.

## The Solution: Delegate Constructors (C++11)

A **delegate constructor** allows one constructor to call another constructor of the *same class* to handle initialization. 

### Syntax
The delegated constructor is called inside the **Member Initializer List**.

```cpp
class Entity {
private:
    int x, y;
    std::string name;

public:
    // "Target" constructor that does the actual work
    Entity(int x_val, int y_val, std::string name_val) 
        : x(x_val), y(y_val), name(name_val) {
        // Complex initialization logic...
    }

    // Delegate Constructor: Forwards to the target constructor
    Entity() : Entity(0, 0, "Default") {}

    // Delegate Constructor: Forwards to target, filling in missing data
    Entity(int x_val, int y_val) : Entity(x_val, y_val, "NoName") {}
};
```

### Important Rule / Caveat
If a constructor delegates to another constructor, **it cannot initialize any other member variables in its initializer list**. 
*   **Invalid:** `Entity(int x) : Entity(x, 0), name("Test") {}` (Compiler Error)
*   You must delegate the entirety of the initialization to the target constructor, though you can still execute code inside the curly braces `{}` of the delegate constructor's body.

# Memory Alignment and Padding (Optimization)

The physical size of a `struct` or `class` in memory is rarely just the exact sum of its member variables. C++ compilers insert empty, wasted bytes known as **padding** to ensure memory is aligned in a way the CPU can process efficiently.

## How Alignment Works

CPUs prefer to read data from memory in "chunks" (powers of 2, 4, 8, etc.). The alignment of a struct is determined by its **largest primitive data type**.

You can check a type's alignment requirement using the `alignof()` keyword:
```cpp
size_t alignment = alignof(GameState);
```

## The Padding Problem

Consider the following struct:
```cpp
struct GameState {
    bool checkpoint; // 1 byte
    float score;     // 4 bytes
    short players;   // 2 bytes
}; 
```
*   **Expected size:** 1 + 4 + 2 = 7 bytes.
*   **Actual size (`sizeof(GameState)`):** 12 bytes.

**Why is it 12 bytes?**
The largest member is `float` (4 bytes), so the struct's `alignof` is 4. The compiler aligns the data into 4-byte blocks:
1.  `bool` takes 1 byte. The next member (`float`) needs to start on a 4-byte boundary. The compiler inserts **3 bytes of padding**.
2.  `float` takes exactly 4 bytes.
3.  `short` takes 2 bytes. To make the total struct size a multiple of the alignment (4), the compiler adds **2 bytes of padding** at the end.
*(Total: 1 + 3 + 4 + 2 + 2 = 12 bytes)*.

*Note: If `float` was changed to `double` (8 bytes), the alignment boundary would become 8 bytes, pushing the total struct size up to 16 bytes due to even more padding.*

## Optimization Strategy: Reordering

To minimize padding and optimize memory usage (which is crucial when creating thousands of objects in game engines or embedded systems), you should **order your member variables from largest to smallest**.

```cpp
struct OptimizedGameState {
    float score;     // 4 bytes (largest type first)
    short players;   // 2 bytes
    bool checkpoint; // 1 byte
}; 
```
*   **Actual size (`sizeof(OptimizedGameState)`):** 8 bytes.
*   By putting the 4-byte float first, the 2-byte short and 1-byte bool can comfortably pack into the next 4-byte block together, leaving only 1 byte of padding at the end. We saved 4 bytes per object.

# Pimpl Idiom (Pointer to Implementation)

The **Pimpl Idiom** (Pointer to Implementation) is a structural design pattern used in C++ to remove compilation dependencies and completely hide implementation details from the client.

## The Problem with Standard Classes

When you put private variables in a header (`.hpp`) file:
1.  **Visibility:** The client can read the header and see your private internal variables/types, breaking true information hiding.
2.  **ABI Instability:** If you add, remove, or reorder private member variables, the actual memory layout (size) of the class changes. 
3.  **Compilation Overhead:** Any change to the private members in the `.hpp` file forces every single `.cpp` file that includes that header to recompile.

## The Pimpl Solution

The Pimpl idiom moves all private data out of the class and into a separate structure defined entirely inside the `.cpp` source file. The `.hpp` file only holds a **forward declaration** of that structure and a pointer to it.

### 1. The Header File (`person.hpp`)
```cpp
#pragma once
#include <memory>
#include <string>

class Person {
public:
    Person(std::string name);
    ~Person();
    void printAttributes() const;

private:
    // Forward declare the implementation structure
    struct PersonImpl; 

    // Only store a pointer. The size of a pointer (8 bytes) never changes.
    std::unique_ptr<PersonImpl> m_impl; 
};
```

### 2. The Source File (`person.cpp`)
```cpp
#include "person.hpp"
#include <iostream>

// Define the hidden structure entirely inside the source file
struct Person::PersonImpl {
    std::string name;
    std::string strength;
    std::string speed;
};

// Constructor: Allocate the implementation object
Person::Person(std::string name) 
    : m_impl(std::make_unique<PersonImpl>()) {
    
    m_impl->name = name;
    m_impl->strength = "N/A";
    m_impl->speed = "N/A";
}

// Default destructor works automatically with unique_ptr
Person::~Person() = default;

void Person::printAttributes() const {
    // Access data through the pointer
    std::cout << m_impl->name << " " << m_impl->strength << "\n";
}
```

## Pros and Cons of Pimpl

| Pros | Cons |
| :--- | :--- |
| **Stable ABI:** The size of the class is exactly the size of one pointer. You can add/remove internal variables without breaking binary compatibility. | **Heap Allocation:** Requires dynamic memory allocation (`new` / `std::make_unique`) when the object is created, which is slower than stack allocation. |
| **Information Hiding:** Clients physically cannot see the internal variables or included headers necessary for the implementation. | **Indirection Overhead:** Accessing variables requires dereferencing a pointer (`m_impl->var`), which can incur a slight performance penalty (cache misses). |
| **Faster Compilation:** Changing the implementation details only requires recompiling the single `.cpp` file, not the clients using the header. | **Complexity:** Requires writing boilerplate code and carefully managing special member functions (e.g., deep copying if the class needs a copy constructor). |

**Modern C++ Note:** Always use `std::unique_ptr` for the implementation pointer to automatically manage memory and avoid memory leaks. Avoid manual `new` and `delete`.


# The `this` Keyword

## Definition and Explanation
In C++, the `this` keyword is a **pointer to the current instance of the object** within a class. Whenever you create an object, memory is allocated specifically for that instance. The `this` pointer stores the memory address of that specific object.

## Primary Use Cases

### 1. Disambiguation
When a member variable and a constructor/function parameter share the exact same name, the compiler prioritizes the local parameter. You use `this->` to explicitly tell the compiler you are referring to the class's member variable.

```cpp
class Person {
private:
    int age;

public:
    // The parameter 'age' shadows the member variable 'age'
    Person(int age) {
        this->age = age; // 'this->age' is the member, 'age' is the parameter
    }
};
```
*Alternative solutions to avoid disambiguation:* 
*   Use naming conventions (e.g., prefixing member variables with `m_` like `m_age`).
*   Use a **Member Initializer List**, where the distinction between parameter and member is implicit: `Person(int age) : age(age) {}`

### 2. Returning the Object's Address
Because `this` is a pointer, you can return it to get the memory address of the object.

```cpp
class Person {
public:
    Person* getAddress() {
        return this; 
    }
};

// Usage:
Person mike;
// mike.getAddress() will equal the memory address &mike
```
*Note:* Whether the object is allocated on the **stack** (`Person mike;`) or the **heap** (`Person* rasheed = new Person();`), `this` correctly points to the respective memory location.

### 3. `delete this;` (Warning)
In very specific, advanced scenarios (like a smart pointer managing its own reference counting and destroying itself), you might see `delete this;` inside a class. **However, this is generally dangerous** and should be avoided in standard code. Let constructors and destructors handle memory management naturally.

# Types of Storage: Stack, Heap, and Static Memory

Understanding where variables are stored dictates their **lifetime** and **scope**.

| Feature | Stack Memory | Heap Memory | Static Storage |
| :--- | :--- | :--- | :--- |
| **Creation** | Automatic (e.g., local variables). | Manual (using `new`). | Compiled directly into the binary/executable. |
| **Lifetime** | Reclaimed when the variable goes out of scope (e.g., closing curly brace `}`). | Persists until explicitly freed (using `delete`). | Persists for the entire duration of the program. |
| **Scope** | Local to the block/function. | Accessible anywhere if you have the pointer. | Depends on declaration (can be local to a function, or global to a file). |

## Static Variables inside Functions
When you declare a local variable with the `static` keyword, it is **allocated exactly once** in the binary. 
*   It does **not** get re-initialized on subsequent function calls. 
*   It retains its value between function calls.
*   Its scope is still limited to the function it was declared in (it cannot be accessed outside).
*   **Modern C++ (C++11 and later):** The initialization of a static local variable is guaranteed to be thread-safe.

### Example
```cpp
void foo() {
    static int s_variable = 0; // Initialized ONLY ONCE
    s_variable += 1;
    std::cout << s_variable << "\n";
}

// Calling foo() 3 times outputs: 1, 2, 3
```

*(Note: You can verify that static variables are baked into the executable using command-line tools like `objdump -t` on Linux or `otool` on Mac, which will show the variable mangled in the symbol table, often in the `.bss` or `.data` section).*

# The `static` Keyword in Classes

Applying `static` to class members changes them from belonging to an *instance* to belonging to the *class itself*.

## Static Member Variables

*   **Scope:** They exist within the scope of the class but live entirely outside of any specific instance.
*   **Shared State:** All instances of the class share the exact same static variable. You do not even need to instantiate the class to access it.
*   **The Linker Error Caveat:** If you declare a static variable inside a class, you **must define (initialize) it outside the class**. If you forget, you will get a **Linker Error** (`undefined reference`). A class is just a blueprint; the definition allocates the actual memory.

```cpp
class API {
public:
    static int major; // Declaration (inside class)
};

// Definition/Initialization (outside class)
// Must be done in the global scope (usually in the .cpp file)
int API::major = 7; 

int main() {
    // Accessed via the Scope Resolution Operator (::)
    std::cout << API::major; 
}
```

### Exception: `const static`
If a static variable is marked `const` (and is of an integral type), it *can* be initialized directly inside the class definition.

```cpp
class API {
public:
    const static int major = 7; // This is valid
};
```

## Static Member Functions

Just like static variables, static functions belong to the class, not an object instance.

### Important Rules for Static Functions
1.  **Cannot access non-static variables:** A static function does not belong to an instance, so it has no concept of instance-specific data.
2.  **Cannot use the `this` pointer:** Because `this` points to an instance, and static functions are instance-independent, `this` is unavailable and will cause a compiler error.
3.  **Can only access other static members.**

```cpp
class API {
private:
    static int major;
    int local_var;

public:
    static int getMajorVersion() {
        // return local_var; // ERROR: Cannot access non-static member
        // return this->major; // ERROR: 'this' is unavailable
        return major; // Valid
    }
};
```

## Structuring Static Classes in Multiple Files
When separating classes with static members into `.hpp` (header) and `.cpp` (source) files:

*   **Header (`.hpp`):** Put the class definition and the `static` declarations here. Do **not** put the variable definitions here, or you will get multiple-definition errors.
*   **Source (`.cpp`):** Put the static variable initialization here. Do **not** write the word `static` again in the `.cpp` file definition.

```cpp
// api.hpp
#pragma once
class API {
public:
    static int major;
    static int getMajor();
};

// api.cpp
#include "api.hpp"
int API::major = 7; // Notice: No 'static' keyword here
int API::getMajor() { // Notice: No 'static' keyword here
    return major;
}
```

# Introduction to Templates

## Definition and Purpose
Templates in C++ (often called **generics** in other languages like Java) are a mechanism to **avoid code duplication (the DRY principle)**. 

Instead of copying and pasting the exact same function multiple times just to change the data types (`int`, `float`, `double`), you write one **template**. A template serves as a **blueprint for the compiler**, instructing it to automatically generate the correct type-specific code for you.

## The Problem (Without Templates)
If you want a function to square a number, you'd have to overload it for every data type. If you miss one (e.g., `float`), the compiler might silently cast your float to an `int`, giving an incorrect mathematical result.

```cpp
int square(int input) { return input * input; }
double square(double input) { return input * input; }
// Tedious, repetitive, and error-prone.
```

## The Solution (With Templates)

You use the `template` keyword followed by template parameters inside angle brackets `< >`. `typename T` acts as a placeholder for whatever data type will be passed in.

```cpp
template <typename T>
T square(T input) {
    return input * input;
}
```

### How the Compiler Handles Templates
When you call a template function, the compiler sees the usage and writes the specific version of that function into the binary behind the scenes.
*   Calling `square(5)` forces the compiler to generate an `int` version.
*   Calling `square(5.5)` forces the compiler to generate a `double` version.
*   (You can use tools like *C++ Insights* to actually view the generated code).

## Template Argument Deduction vs. Explicit Instantiation

Modern C++ is smart enough to figure out the intended type based on the argument you pass in. This is called **Template Argument Deduction**.

```cpp
// Implicit Deduction: Compiler deduces T is a double
std::cout << square(5.5); 
```

However, you can also be **explicit** about which version of the template you want the compiler to generate or use by providing the type in angle brackets `< >`.

```cpp
// Explicit Instantiation: Forces the float version
std::cout << square<float>(6.5f); 
```

*(Note: This angle-bracket syntax is the exact same mechanism used in the Standard Template Library (STL) when you create a `std::vector<int>`. `vector` is the template, and `int` is the explicit template parameter).*


# Function Templates

## Definition and Motivation
Templates (often referred to as **generics** in other languages) provide a way to write generic, reusable code. They allow functions or classes to operate with any data type, helping developers strictly follow the **DRY (Don't Repeat Yourself)** principle by avoiding copy-pasting code for different data types.

Templates are not a strictly Modern C++ feature; they have been part of the language since before C++98. However, Modern C++ (C++11/20) introduces powerful enhancements to how templates are written and used.

## Templates vs. Function Overloading

| Feature | Function Overloading | Templates |
| :--- | :--- | :--- |
| **Best Used For** | Specific, well-defined mathematical/built-in types. | Truly generic operations that should apply to *any* compatible type (e.g., containers, vectors, custom classes). |
| **Maintenance** | Requires writing and maintaining separate code for each type (`int`, `float`, `double`). | Requires writing a single blueprint; the compiler generates the rest. |

## Anatomy of a Function Template

A template acts as a **blueprint** for the compiler to generate code. 

### Syntax
```cpp
// Template parameter list
template <typename T> 
T square(T input) {
    return input * input;
}
```

*   `template`: The keyword introducing a template.
*   `<typename T>`: The **template parameter list**. 
*   `typename`: Specifies that `T` is a type. You can also use the keyword `class` here (`template <class T>`); in this context, they are identical. `typename` is the modern convention.
*   `T`: A placeholder name for the data type. Its scope is restricted to the function that immediately follows it.

### Template Instantiation
When you call a template function, the compiler performs **Template Instantiation**. It reads the blueprint and *generates* the actual C++ code (the overloaded function) for the specific type you used.

```cpp
square(5);     // Compiler implicitly deduces T = int, generates an integer version
square<float>(5.5f); // Explicitly tells the compiler to generate a float version
```
*Note: The compiler only generates code for types that are actually used in your program. If you never call `square<double>`, the compiler will not bloat your binary with a double version.*

## C++20: Abbreviated Function Templates

In C++20, you can bypass the `template <typename T>` syntax entirely for simple function templates by using the `auto` keyword in the function parameter list. The compiler automatically deduces it as a template under the hood.

```cpp
// C++20 Abbreviated Function Template
auto square2(auto input) {
    return input * input;
}
```

# Multiple Template Parameters and Non-Type Parameters

## Multiple Template Types
You can pass an arbitrary number of types into the template parameter list.

```cpp
template <typename T1, typename T2>
void printTypes(T1 input1, T2 input2) {
    std::cout << input1 << "\n" << input2 << "\n";
}

// Usage:
printTypes<int, float>(5, 3.14f);
```

### Caveat: Template Code Bloat / Code Explosion
Every unique combination of template arguments results in a completely new, separate function being generated in the compiled binary.
*   Calling `printTypes<int, float>` generates one function.
*   Calling `printTypes<float, int>` generates a *second, entirely separate function*.
Overusing templates with highly variable type combinations can lead to significantly larger executable sizes.

*(Tip: You can use `#include <typeinfo>` and print `typeid(T).name()` inside the template to inspect the exact types the compiler instantiated).*

## Non-Type Template Parameters (NTTP)
Template parameters do not always have to be data types (`typename T`). They can also be known, compile-time values (like `int`, `size_t`, etc.). 

A standard library example is `std::array<int, 5>`, which takes a data type (`int`) and a non-type value (`5` for size).

### Example: A fixed-iteration function
```cpp
template <typename T, size_t N>
void printNTimes(T input) {
    for (size_t i = 0; i < N; ++i) {
        std::cout << input << "\n";
    }
}

// Usage:
printNTimes<std::string, 5>("Hello");
```

**Caveat:** Just like with types, calling `printNTimes` with `N=3`, `N=4`, and `N=5` will cause the compiler to generate **three distinct functions**.

# Full Template Specialization

Sometimes, a generic template does not work correctly for a specific data type, and you need to provide a custom implementation just for that type. This is known as **Template Specialization**.

## The Motivation: Floating-Point Equality
A generic `equals` template works fine for integers, but fails for floating-point numbers due to precision loss.

```cpp
// Generic Template
template <typename T>
bool isEqual(T a, T b) {
    return a == b; // Dangerous for floats/doubles
}
```

## Explicit Full Specialization Syntax
To override the generic template for a specific type (e.g., `float`), you leave the template parameter list empty `template <>` and specify the type in angle brackets next to the function name.

```cpp
#include <cmath>

// Full Specialization for 'float'
template <>
bool isEqual<float>(float a, float b) {
    // Check if the absolute difference is within a small epsilon
    return std::abs(a - b) < 0.00001f; 
}
```

When the compiler encounters `isEqual(1.0f, 1.0000001f)`, it will see your specialized version and use it instead of generating a generic one.

**Important Caveat:** 
A specialization for `float` **does not apply** to `double`. If you pass `double` arguments, the compiler will fall back to generating the unsafe generic `a == b` implementation. You must provide a separate specialization for `double`.

```cpp
template <>
bool isEqual<double>(double a, double b) {
    return std::abs(a - b) < 0.000000001; 
}
```

# Variadic Function Templates

**Variadic templates** allow a function to accept an arbitrary (variable) number of arguments of any type. 

## C-style `varargs` vs. C++ Variadic Templates
| C-style (`<stdarg.h>`) | C++ Variadic Templates |
| :--- | :--- |
| e.g., `printf("%d %f", a, b)` | Template-driven generation |
| **Runtime Overhead:** The program computes argument counts and types dynamically at runtime. | **Compile-Time Generation:** The compiler writes the exact, type-safe function during compilation. Zero runtime overhead. |
| **Type-Unsafe:** Passing the wrong format specifier causes undefined behavior. | **Type-Safe:** The compiler fully knows and checks the types at compile time. |

## The Parameter Pack Syntax
Variadic templates use an ellipsis (`...`) known as a **Parameter Pack**.
*   `typename... Types` (Template parameter pack: a list of types)
*   `Types... args` (Function parameter pack: a list of arguments of those types)

## Implementation Strategy: Recursive Peeling
To process a parameter pack, you typically use a recursive-like pattern:
1.  A **Base Case** function that handles the final single argument.
2.  A **Variadic Function** that handles the *first* argument explicitly, and then passes the *rest* of the parameter pack recursively to itself.

### Example: A Variadic `sum` Function
```cpp
// 1. Base Case (Must be defined BEFORE the variadic function)
template <typename T>
T sum(T arg) {
    return arg;
}

// 2. Variadic Template (Recursive Step)
template <typename T, typename... Args>
T sum(T start, Args... args) {
    // Adds the first item to the sum of the remaining items
    return start + sum(args...); 
}

// Usage:
// sum(1, 2, 3, 4, 5); -> 1 + sum(2, 3, 4, 5) -> 2 + sum(3, 4, 5)...
```

### Important Caveat: Mixed Types in Recursion
Because the return type of the recursive step (`T`) relies on the *first* argument of that exact instantiation, mixing data types (e.g., `int` and `double`) can cause bugs due to unintended type truncation.

If you call `sum(1, 2.2, 3.7, 4, 5)`:
*   The first type `T` is deduced as `int`.
*   The operation will downcast the subsequent `double` additions into `int`, resulting in an incorrect answer (e.g., `14` instead of `15.9`).

**Solutions for Mixed Types:**
1.  **Explicitly pass the correct type first:** `sum(1.0, 2.2, 3.7, 4, 5)` ensures the return type propagates as a `double`.
2.  **Explicit Return Type:** Explicitly specify the template type upon calling `sum<double>(...)`.
3.  **Modern standard library utilities:** Use `<type_traits>` features like `std::common_type_t` to dynamically evaluate what the safest unified return type should be (e.g., yielding `double` if mixing `int` and `double`).

### Code Bloat Warning
Variadic templates recursively instantiate new functions for *every remaining size and type combination* of the parameter pack. Calling `sum(1, 2.2, 3.7)` generates:
1. `sum(int, double, double)`
2. `sum(double, double)`
3. `sum(double)` (Base case)

Be mindful of binary bloat when overusing variadic templates on varied type signatures in resource-constrained environments.


# Advanced Function Templates and Return Type Deduction

When writing template functions, working with primitive types (like `int` and `float`) is straightforward. However, things become complex when operating on large user-defined types (like `Matrix` or `Vector` classes) or multiplying completely different types together.

## 1. Optimization: Pass by `const` Reference
When dealing with large data types in templates, you should avoid passing parameters by value to prevent expensive copies. Instead, pass by `const` reference.

```cpp
// Less efficient: Passes by value (creates copies)
template <typename T>
T multiply(T a, T b) { return a * b; }

// Optimized: Passes by const reference
template <typename T>
T multiply(const T& a, const T& b) { return a * b; }
```

## 2. Handling Multiple Types and Return Type Deduction
If you want to multiply two completely different types (e.g., a `Matrix` and a `Vector2`), the function needs two template parameters (`T1` and `T2`).

**The Problem:** What should the return type be? If you multiply a `Matrix` by a `Vector2`, the result is a `Vector2`. You cannot simply hardcode `T1` or `T2` as the return type. 

### Solution A: `auto` Return Type (C++14 and beyond)
Modern C++ compilers can automatically deduce the return type based on the operation inside the function.

```cpp
template <typename T1, typename T2>
auto multiply(const T1& a, const T2& b) {
    return a * b; // Compiler deduces the correct return type
}
```

### Solution B: Trailing Return Type with `decltype` (C++11 / Explicit approach)
If you need to be explicit or are working in an older codebase, you can use a **trailing return type** combined with `decltype`. `decltype` evaluates an expression (`a * b`) at compile time and extracts its resulting type.

```cpp
template <typename T1, typename T2>
auto multiply(const T1& a, const T2& b) -> decltype(a * b) {
    return a * b; 
}
```

# Class Templates

Class templates (often seen in the Standard Template Library, e.g., `std::vector`) allow you to create a blueprint for a user-defined type (a `class` or `struct`) that operates on generic data types.

## Creating a Class Template

To make a class a template, declare the template parameter list immediately above the class definition, and substitute the generic type `T` wherever necessary.

```cpp
template <typename T>
class Container {
private:
    T* m_data; // Pointer to generic type
public:
    // Constructor allocating an array of generic types
    Container(int size) {
        m_data = new T[size]; 
    }

    ~Container() {
        delete[] m_data;
    }
};

// Usage (Explicit instantiation):
Container<int> c1(10);     // Instantiates an integer container
Container<double> c2(5);   // Instantiates a double container
```

## Non-Type Template Parameters (NTTP)
Template parameters are not restricted to data types (`typename T`). You can also pass fixed, compile-time values (like `int`, `size_t`, etc.). 

This is identical to how `std::array<int, 5>` works.

```cpp
template <typename T, int Size>
class Container {
private:
    T* m_data;
public:
    Container() {
        m_data = new T[Size]; // Size is known at compile-time
    }
};

// Usage:
Container<int, 5> c3;
Container<int, 7> c4;
```
**Important Note:** The compiler treats `Container<int, 5>` and `Container<int, 7>` as **two completely different data types**. It generates a completely separate class definition for each unique set of template parameters.

# Static Member Variables in Class Templates

Static member variables behave uniquely when placed inside templated classes.

## How Static Variables Work in Templates
In a normal class, a `static` variable is shared across all instances of that class.
In a **class template**, a `static` variable is shared **only across instances of the exact same template instantiation.**

*   All instances of `Container<int, 5>` share one `m_variable`.
*   All instances of `Container<double, 5>` share a completely separate `m_variable`.

## Defining the Static Variable (Fixing the Linker Error)
Just like in standard classes, declaring a `static` variable inside a class template only tells the compiler it exists. If you try to use it without defining it outside the class, you will get a **Linker Error (`undefined reference`)**.

### Syntax for Definition

```cpp
// 1. Class Declaration
template <typename T, int Size>
class Container {
public:
    static T m_variable; 
};

// 2. Definition (Required to avoid linker errors)
// You must restate the template parameters and use the scope resolution operator.
template <typename T, int Size>
T Container<T, Size>::m_variable = 0; // Initialize with a default value

int main() {
    // Usage:
    Container<int, 5>::m_variable = 157;
    
    // This outputs 157
    std::cout << Container<int, 5>::m_variable << "\n";
    
    // This outputs 0 (it is a completely separate class instantiation)
    std::cout << Container<int, 7>::m_variable << "\n"; 
}
```

# CTAD: Class Template Argument Deduction (C++17)

**CTAD (Class Template Argument Deduction)** is a modern C++ feature introduced in C++17. It allows the compiler to automatically figure out (deduce) the template types of a class based on the arguments passed to its constructor.

## The Problem (Pre-C++17)
Historically, when creating an object of a class template, you had to explicitly write out the template types in the angle brackets `< >`.

```cpp
template <typename T1, typename T2>
struct Entry {
    T1 key;
    T2 value;
    
    Entry(T1 k, T2 v) : key(k), value(v) {}
};

// Pre-C++17: Explicit types required
Entry<int, float> e(1, 3.14f);
```

## The Solution (C++17 and CTAD)
With CTAD, if the compiler has enough information from the constructor parameters, you can omit the angle brackets completely.

```cpp
// C++17 CTAD: Types are automatically deduced
Entry e(1, 3.14f); // Compiler knows T1 is int, T2 is float
```

### Standard Library Usage
CTAD is extremely useful and commonly seen with standard library containers like `std::vector` and `std::pair`.

```cpp
#include <vector>

// Pre-C++17
std::vector<int> v1 = {1, 2, 3};

// C++17 CTAD
std::vector v2 = {1, 2, 3}; // Deduces std::vector<int>
```

### Common Mistake / Caveat: Ambiguity
CTAD strictly requires the compiler to be able to make a definitive guess. If you provide conflicting types, the compiler will fail to deduce the template parameter.

```cpp
// ERROR: Compilation fails. 
// Is it a vector of int or a vector of float?
std::vector v3 = {1, 3.0f}; 

// FIX: Make the types consistent, or explicitly provide <float>
std::vector v4 = {1.0f, 3.0f}; 
```
